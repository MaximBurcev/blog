# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Docker Environment

All PHP/Artisan commands must be run inside the `laravel.test` container (Laravel Sail). Check the running container name with `docker ps`, then:

```bash
docker exec -it <container_name> php artisan <command>
# e.g.: docker exec -it laravellocal-laravel.test-1 php artisan tinker
```

Alternative via Sail:
```bash
./vendor/bin/sail artisan <command>
```

## Architecture Overview

### Admin Interface

**Filament Panel** at `/filament` — the only admin panel. Built with Filament 3, auto-discovers resources in `app/Filament/Resources/`. Configured in `app/Providers/Filament/FilamentPanelProvider.php`; access is gated by `User::canAccessPanel()` (role `UserRole::Admin`).

The former custom AdminLTE admin at `/admin` was disabled on 2026-07-27 and removed on 2026-07-30 together with its controllers, form requests, Blade views, Livewire components and the `jeroennoten/laravel-adminlte` package — everything had moved to Filament. The `admin` middleware alias (`AdminMiddleware`) is kept for future protected routes, though nothing uses it right now.

### Database

Single MySQL database, default `mysql` connection (`config/database.php`), configured via `DB_*` env vars. The former `secondary` connection (remote posts DB) was decommissioned in July 2026 — all models, including `Post`, use the default connection.

### Controller Pattern

All controllers are single-action classes — each HTTP action (index, show, store, etc.) has its own dedicated controller class. Example: `Post/ShowController.php`, `Category/IndexController.php`.

### Services (`app/Service/`)

- **PostService** — creates/updates posts, handles image upload to `storage/public/images`, optionally runs translation via `TranslateService`
- **ReleaseService** — stores Release URLs, parses external pages with CSS selectors (via Symfony DomCrawler), dispatches `StorePostJob` for each found link. Configurable via `config/releases.php`
- **ContentImageService** — downloads external images referenced in post content, saves them locally to `storage/public/images/content/`
- **TranslateService** — wraps Google Translate for post content translation

### Async Jobs (`app/Jobs/`)

- **StorePostJob** — fetches an external URL, extracts content by CSS selector, translates text nodes to Russian via Google Translate (skipping `<code>` tags), downloads images via `ContentImageService`, then calls `PostService::store()`
- **ParseReleaseJob** — parses links from a release URL
- **GenerateImageVariantsJob** — generates WebP variants for post images

`StoreUserJob` was removed on 2026-08-09: it was never dispatched anywhere, mass-assigned `$data` wholesale (including `role`, i.e. a ready-made privilege escalation for whoever wired it up), and put the plaintext password into the queue payload.

### News section

`/news` — лента новостей из секции «News and Announcements» дайджеста PHP Weekly
(тех же `Release`, что питают статьи). Новость — это `Post` с флагом `is_news`,
а не отдельная модель: разбирается, переводится и хранится тем же пайплайном,
поэтому у неё есть полный текст, картинки и своя страница `/news/{code}`.
Отдельная модель означала бы дублирование всего `StorePostJob` целиком.

Главная (`Main\IndexController`) фильтрует по `is_news` через скоуп `articles()`.
Остальные выборки — нет: у новости есть категория и теги (их проставляет
парсер), поэтому она равноправно попадает в `/categories/{code}`,
`/tags/{code}`, поиск, RSS и блок «похожие». Ссылку на неё обязан давать
**`Post::permalink()`**, а не `route('post.show')`: адреса разведены, и
`Post\ShowController` отвечает на «чужой» 301-м редиректом — то есть каждая
такая ссылка была бы лишним хопом. Метод зовётся `permalink()`, а не `url()`,
потому что колонка `posts.url` (адрес первоисточника) уже занята: одноимённый
метод Eloquent принимает за связь и валит `$post->url` в LogicException.
Выборкам с сужающим `select()` нужен `is_news` в списке колонок — иначе он
молча читается как `null` и все новости получают адрес статьи.

- `App\Support\NewsDigestParser` — разбор секции (без ввода-вывода, покрыт тестами)
- `App\Service\NewsImportService` — **только** разбор секции и постановка
  `StorePostJob` на каждую ссылку; перевод и сохранение делает джоба и
  `PostService`. Дедуп — предварительной выборкой `Post::where('url', …)`,
  UNIQUE-индекс на `posts.url` тут второй рубеж, а не первый
- `php artisan news:import [url]` — **только вручную, снят с расписания
  24.08.2026**. `NewsImportService` намеренно перезапускает заглушки
  (`parse_status = failed`) ради второго шанса временному сбою, но потолка у
  повторов нет, а часть ссылок секции — ролики YouTube, главная php.net и
  страницы релизов GitHub, где статьи не существует. Журнал `llm_calls` показал
  счёт: 24.08 все 11 вызовов модели за сутки пришлись на такие заглушки — 55%
  бесплатной квоты каждое утро в никуда. Причины и условия возврата — в
  комментарии `app/Console/Kernel.php`, отсутствие в расписании закреплено
  `ImportNewsCommandTest`
- Без аргумента команда обходит **все** заведённые релизы и воспроизводит тот же
  холостой ход — до починки звать её с конкретным адресом дайджеста
- **Кнопки импорта в админке сейчас нет.** Она была (`NewsResource\Pages\ListNews`,
  действие «Импортировать из дайджестов») и удалена вместе со всем
  `NewsResource` в `67208d5`, когда новость стала флагом `Post`. Тогда её
  заменяло расписание; теперь не заменяет ничто, так что при возврате импорта
  кнопку стоит завести заново
- Осторожно с порядком: `RELEASE_SECTION_HEADINGS` на проде не задан, то есть
  кнопка «Спарсить» у релиза забирает ссылки из **всех** секций дайджеста,
  включая новостную, и заводит их обычными статьями (`is_news = false`). После
  неё `news:import` эти адреса уже пропустит (они существуют и не `failed`), и
  `/news` останется пустым. Пока импорт шёл в 07:00, он почти всегда успевал
  первым; теперь оба пути ручные и очерёдность имеет значение

### Дайджест JavaScript Weekly

Второй источник рядом с PHP Weekly, и свёрстан он иначе. Выпуск состоит из
блоков двух видов: заголовочный материал — `table.el-item` со ссылкой в
`span.mainlink`, компактные секции («In Brief», «Releases», «Articles and
Videos») — `table.content.el-md`, где ссылка лежит прямо в `<p>`. Прежний
селектор `li a:first-of-type` видел только часть второго вида: на выпуске 799
это 18 ссылок против 35 и **ни одного** из 13 заголовочных материалов, то есть
ровно тех статей, ради которых дайджест и разбирается.

`:first-of-type` у `el-md` оставлен: первая ссылка абзаца заголовочная,
остальные — вторичные упоминания в тексте пункта. Цена известна и принята — в
секции «Releases» несколько релизов перечислены через запятую в одном `<p>`,
и берётся только первый (на 799 потеряны React Native, ESLint, Axios, pnpm).
Без `:first-of-type` в очередь добавляется восемь вторичных ссылок на выпуск,
а релизные заметки для блога наименее ценны.

**Реклама отсеивается по разметке, а не по доменам.** Спонсорский пункт
свёрстан ровно как обычный — та же таблица с тем же классом, та же ссылка в
`span.mainlink`; отличает его только метка `span.tag-sponsor` внутри блока.
Классы у рекламного и обычного пункта совпадают, а подняться от ссылки к
предку CSS не умеет (`:has()` в Symfony CssSelector нет) — отсюда пара
«контейнер пункта + метка» в `parser_sponsor_markers_by_domain`. Список
доменов тут бесполезен: спонсоры меняются каждую неделю (webflow, fidelity,
paradedb — три разных в одном выпуске), и блокировка по хосту била бы заодно
по нормальным статьям с того же домена.

Адреса рекламных ссылок собираются **один раз на документ**
(`ReleaseService::sponsoredHrefs()`): идём от метки вверх к пункту и забираем
оттуда все ссылки. Проверять каждую найденную ссылку подъёмом к предку нельзя
— `Crawler::closest()` заново компилирует CSS-селектор на каждом уровне
вёрстки, а вёрстка дайджеста табличная: на выпуск выходило под три сотни
разборов селектора ради двух-трёх меток. Отсев применяется в **обеих** ветках
извлечения, включая секционную (`td.bodyContent`), которой разбирается PHP
Weekly: иначе правило, заведённое для него, выглядело бы рабочим и молча не
работало.

Источники выпуска разобраны и заведены в `site_selectors` миграцией
(14 доменов, замер 26.08.2026), в `domain_selectors` те же значения остаются
фолбэком. У большинства годится голый `article`, у Docusaurus — `.markdown`,
у VitePress — `.content-container`, у nodejs.org только `main` (классы вёрстки
хешируются сборкой и меняются с каждым релизом сайта).

**Стоимость источника меряется в HTML, а не в тексте.** `GeminiTranslator`
режет на куски то, что отдаёт `StorePostJob`, а отдаёт он `saveHTML()` узлов:
у tkdodo.eu текста 44 КБ, а разметки 536 КБ — 27 запросов к модели на одну
статью при суточной квоте 60 на всю цепочку моделей. Второй такой источник —
runjs.app (391 КБ, 20 запросов). Оба заведены осознанно (заглушка вместо
статьи хуже), но выпуск, где таких материалов несколько, съедает квоту
целиком, а `budget_seconds = 240` оборвёт перевод раньше, чем кончатся куски,
и хвост уедет на скрейпер с отметкой «перевод неполный».

Чего этот пайплайн не берёт и почему:

- **SPA** (solidjs.com отдаёт 3 КБ с пустым `#app`) — FlareSolverr включается
  только на антибот-заглушку (`isChallengePage()`), а не на «селектор ничего
  не нашёл». Пока такие ссылки становятся заглушками
- **Сайты без контейнера статьи** (tanstack.com, waku.gg, formisch.dev) —
  сплошные Tailwind-утилиты, `.flex`/`.w-full` склеивают по 100–200 узлов.
  Грамматика селекторов проекта (`тег` / `.class` / `#id`) такое не выражает
- **Гигантские релизные посты**: у bun.com одного текста 339 000 символов —
  правило для домена не заводилось вовсе

Два ограничения, о которых стоит помнить при первом прогоне. Выпуск даёт
**24 ссылки** после всех отсевов при `max_links = 20` по умолчанию: пока
селектор находил 18, потолок не срабатывал ни разу, а теперь режется хвост уже
из настоящих статей — мусор отсеивается раньше среза. Молча это больше не
происходит, `processLinks()` пишет предупреждение с адресами отброшенных;
лечится `RELEASE_MAX_LINKS`. И вторая: 24 статьи — это минимум 48 запросов к
модели, то есть вся дневная бесплатная квота цепочки, даже без дорогих
источников.

### Оригинал статьи (`?lang=en`)

Английский исходник лежит в `posts.content_orig` с 22.02.2026. Над статьёй —
плашка «Перевод статьи с …» (`Post::isMachineTranslated()`: сохранённый оригинал
либо успешно разобранный источник — одного `url` мало, он остаётся и у заглушек
с `parse_status = failed`, текст которых пишет админ руками). Оттуда же ссылка
на `?lang=en` — тот же адрес, то же тело страницы, другой язык статьи.

Версия оригинала отдаёт `noindex, follow` и **самоссылочный** canonical. Пара
«noindex + canonical на другой адрес» противоречива: Google документированно
переносит `noindex` на цель канонизации, то есть выбил бы из выдачи сам
перевод. `?lang=en` у поста без оригинала — 302 (не 301: оригинал появится,
если заглушку разберут повторно, а постоянный редирект браузер кэширует
навсегда). Редирект между `/posts/{code}` и `/news/{code}` сохраняет query,
иначе переключатель роняет читателя обратно в перевод.

Тело оригинала рендерится через **`Post::originalBody()`**, а не сырую колонку:
мутатор `setContentOrigAttribute` появился на пять месяцев позже самой колонки,
поэтому записи с 22.02 по 27.07.2026 хранят необработанный HTML
страницы-источника (у двух уцелел `<iframe>`). Санитайзинг на выводе не зависит
от того, прогнали ли где-то `posts:resanitize` — а команда теперь чистит обе
колонки. Заодно из оригинала вырезаются картинки с чужих доменов: их
локализует `ContentImageService`, но только для перевода, и без этого браузер
читателя ходил бы за каждой на medium/dev.to (плюс 403 хотлинка). Результат
кэшируется до следующей правки поста.

`content_orig` идёт и в поисковый индекс: термины вроде «queue worker» или
«readonly properties» в переводе остаются английскими не всегда, и запрос по
ним не находил статью, которая целиком про них. **После деплоя нужен
`php artisan scout:import "App\Models\Post"`** — Scout переиндексирует запись
только при её сохранении, иначе у всего архива в документе не будет нового
поля. `SCOUT_QUEUE=true`, так что импорт разбирает воркер очереди.

### Аналитика просмотров

`Блог → Аналитика` (`App\Filament\Pages\Analytics`) — единственный потребитель
таблицы `post_views`, кроме счётчика под заголовком статьи. Плитки трафика,
график по дням (`flowframe/laravel-trend`) и топ читаемых постов; общий фильтр
периода живёт на странице (трейт `HasFiltersForm`) и раздаётся виджетам через
`getWidgetData()`.

Виджеты лежат в `app/Filament/Analytics/Widgets`, а **не** в
`app/Filament/Widgets`: вторая директория раздаётся `discoverWidgets`, и всё из
неё Filament сам выводит на дашборде — там нет фильтра периода, а дашборд
отвечает за состояние парсинга, не за трафик. Расплата — их приходится
регистрировать в `FilamentPanelProvider` через `->livewireComponents([...])`:
первый рендер проходит и без этого, но snapshot Livewire хранит **имя**
компонента, и без алиаса в реестре любое действие внутри виджета (смена
периода, сортировка, пагинация) отвечает `ComponentNotFoundException`.
Регрессия закрыта `AnalyticsPageTest::test_analytics_widgets_are_resolvable_by_livewire_name`
— рендером страницы она не ловится.

Окна сравнения строятся одинаковой длины (`AnalyticsPeriod::previousEndsAt()`):
текущий период — это N-1 полных суток плюс прошедшая часть сегодняшнего дня,
поэтому предыдущий обрезается тем же временем суток. Иначе каждое утро при
ровном трафике плитки показывали бы падение, которого нет. Период приходит из
query-string (`#[Url]`), поэтому `AnalyticsPeriod::days()` сверяет его с белым
списком: `?filters[period]=100000` иначе означал бы скан всей `post_views`.

`post_views` — самая быстрорастущая таблица блога, отсюда: индекс на одном
`viewed_at` (составной `(post_id, viewed_at)` для фильтра без `post_id` не
работает), все плитки периода — одним проходом условной агрегации, а «всего
просмотров» (единственный неограниченный `COUNT(*)`) — из кэша на 10 минут.

**Глубина чтения** (`ReadingDepth`) считает РАЗНЫЕ статьи на читателя
(`COUNT(DISTINCT post_id)`), а не просмотры: дедуп в `PostViewService` держится
24 часа, а окно виджета до 90 дней, и возврат к той же статье через неделю даёт
вторую запись — по `COUNT(*)` такой читатель попадал бы в «идут дальше первой»
и завышал ровно ту долю, которую виджет измеряет. Единица счёта — читатель за
период, а не визит: границ сессии в таблице нет, склеить просмотры в посещения
нечем.

**Темп публикаций** (`PublishingPace`) считает по `posts.parsed_at` и
`posts.published_at`, но **не по `created_at`**: там лежит дата публикации
оригинала у источника (её вытаскивает `StorePostJob`), и на проде 135 постов из
147 разобраны позже своего `created_at` — разрыв доходит до 150 дней. По
`created_at` виджет показывал бы, когда материал вышел у автора, выдавая это за
темп нашего парсера.

`posts.published_at` появилась 20.08.2026 и заполняется хуком `saving` в
`Post::booted()` — снять галочку черновика можно из формы, из массового
действия и из tinker, и помнить об этом в каждом месте нельзя. Дата ставится
один раз: снятая и возвращённая публикация не должна выглядеть новой, иначе
темп накрутится правкой старых постов. Историческим записям миграция проставила
`updated_at` — приближение, поэтому периоды до 20.08.2026 виджет помечает как
неполные, ровно как `PostView::ATTRIBUTION_SINCE` делает с источниками
переходов. Осторожно с именами: `PostData::$publishedAt` — это дата оригинала и
кладётся в `created_at`, а `posts.published_at` — наш момент публикации; в
`$fillable` последняя намеренно не входит.

Очередь черновиков считается как «не сломанные» (`parse_status != failed`), а не
«ровно `ok`»: колонка nullable без default, у постов старше 30.07.2026 и у
всего, что заводят руками в админке, там `NULL` — условие `= ok` молча
выкидывало бы их из очереди.

### Расход на языковую модель

`llm_calls` — журнал обращений к Gemini: по строке на вызов, пишет только
`GeminiTranslator::record()` (единственная точка выхода из `ask()`, поэтому
«вызовов в журнале меньше, чем было» по построению не бывает). Читают журнал
виджет `Блог → Аналитика → Расход на перевод` и команда чистки — больше никто.

До него про LLM было известно ровно одно — имя движка в `posts.translated_by`.
Токены Gemini присылает сам, в `usageMetadata` каждого ответа; код это поле
**выбрасывал**, а длительность, повторы и причины отказов жили в
`Log::warning` до ближайшей ротации. Вопрос «сколько стоит пост» ответа не имел.

Записывается и то, что деньгами кончилось впустую: ответ, забракованный
`TranslatedHtmlValidator` (`outcome = rejected`, проставляется вторым шагом —
годность разметки выясняется уже после возврата из `ask()`), и обрезанный по
`MAX_TOKENS` (`truncated`). За оба мы платим полностью, а статьи не получаем;
удалив их, отчёт занизил бы расход ровно на ту долю, которую хотелось бы не
замечать. Вызовы, не дошедшие до сети (`no_key`, `budget`), тоже в журнале, но
с `duration_ms = NULL`: ноль означал бы мгновенный ответ и портил среднюю.

**Промпта и ответа модели там нет.** Тело статьи и так лежит в
`posts.content_orig`, а второй экземпляр рядом с расходами удвоил бы ежедневный
архив ради данных, на которые ни один отчёт не смотрит. При ошибке остаётся
класс исключения и обрезанное сообщение — этого хватает, чтобы отличить таймаут
от «регион не поддерживается». Тело чужого ответа прогоняется через
`mb_convert_encoding`: страница ошибки от прокси текстом быть не обязана, а
невалидный UTF-8 роняет INSERT — вызов пропал бы из журнала целиком.

От вердикта валидатора в `error` попадает только **вид** причины
(`LlmCall::category()`): `TranslatedHtmlValidator` дописывает к ней до 60
символов кода из самой статьи, а это и нарушение предыдущего абзаца, и смерть
отчёта — с уликой каждый брак становится уникальной строкой, и «по каким
причинам браковали» вырождается в список из N причин вместо трёх с числами.
Полный текст остаётся в `laravel.log`, где он и нужен, поштучно.

**Денег в таблице тоже нет** — только токены. Цена лежит в
`config/translation.php → gemini.prices`, ключ — имя модели: `GEMINI_MODEL`
меняется через env, и складывать токены разной цены в одну кучу нельзя. Записав
стоимость колонкой, мы заморозили бы историю по прайсу того дня, когда строка
легла в таблицу. По умолчанию цен **нет намеренно**: число, вписанное однажды
«примерно», молча разъезжается с реальностью, поэтому пока строки нет, виджет
показывает токены и прямо пишет, что цена не задана. Модель без цены не
обнуляет сумму, а выносится в остаток отдельной подписью.

Цена поста считается как расход периода ÷ посты с `translated_by = 'gemini'` и
`parsed_at` в периоде. Числитель включает промахи, уведшие статью на скрейпер, —
это намеренно: они оплачены.

Повторы (`attempts`) считаются в колбэке `when:` у `->retry()` — другого места,
где видна каждая неудачная попытка, у клиента нет; потолок по числу задержек,
потому что на последней попытке колбэк вызывается, а повтора за ним уже нет.
429 у бесплатного тира — рабочий режим, но задержки доходят до 45 секунд, и
рост этого счётчика — единственное объяснение, почему разбор статей вдруг пополз.

**429, переживший всю цепочку повторов, размыкает движок на `quota_pause_seconds`
(час), а не на обычные пять минут.** «Слишком часто» и «на сегодня всё» приходят
одинаковым `RESOURCE_EXHAUSTED`, и различать их по тексту нельзя — прозу Google
вправе переписать в любой день. Различаем рассуждением о времени: если **фактически
прождали** дольше минутного окна, поминутный лимит за это время успел смениться и
дело не в нём. Именно прождали, а не «собирались» по сумме `retry_delays_ms`:
обрыв связи возвращается мгновенно, и цепочка из трёх обрывов укладывается в
секунды при тех же 62 в конфиге. Отсюда же замер через `CarbonImmutable`, а не
`microtime` — тем же часам подчиняется `Sleep`, поэтому в тестах сон подделывается
(`Sleep::fake(syncWithCarbon: true)`) вместо честной минуты простоя.

Цена ошибки несимметрична: суточная
квота не восстановится ни через минуту, ни через пять, и без паузы каждая
следующая статья платит за один и тот же отказ полной цепочкой ожиданий —
62 секунды на заголовке и столько же на теле. Так и вышло на проде 21.08.2026:
бесплатные 20 запросов кончились к 18:15, и 18 статей подряд отдали на повторы
около сорока минут воркера, чтобы всё равно уйти на скрейпер. Порог короче
минуты паузу не ставит: всплеск наказывать незачем.

`FallbackTranslator::markDown()` хранит в кэше **момент** окончания паузы и
никогда её не укорачивает: рядовая пятиминутная, легшая поверх часовой квотной,
вернула бы нас к заведомо провальным попыткам через пять минут — и так по кругу
до самого сброса квоты. Ноль в `quota_pause_seconds` означает «значения нет» и
откатывает к обычной паузе, а не отменяет её; общий рубильник по-прежнему один —
`circuit_breaker_seconds = 0`.

**Бесплатная квота считается ПО МОДЕЛИ.** Google называет это прямо в
структурированной ошибке 429: `quotaId = GenerateRequestsPerDayPerProjectPerModel-FreeTier`,
`quotaValue = 20`. Замерено 24.08.2026 — одним ключом в одну секунду
`gemini-3.6-flash` отдавал 429, а `gemini-3.5-flash` отвечал 200. Ходя всегда в
одну модель, мы использовали треть доступного.

Отсюда цепочка моделей: `GEMINI_MODEL` + `GEMINI_FALLBACK_MODELS`, собирается в
`AppServiceProvider` через вложенные `FallbackTranslator` (он сам реализует
`Translator`, поэтому вкладывается сам в себя без единой правки). Три модели —
60 запросов в сутки вместо 20, бесплатно и на том же ключе. Статья стоит
минимум два запроса (заголовок и тело, плюс по запросу на каждый кусок длиннее
20 000 символов).

**`GeminiTranslator::name()` возвращает имя МОДЕЛИ, а не «gemini».** По нему
размыкается предохранитель и заполняется `posts.translated_by`; верни он общее
имя — исчерпание квоты у одной модели гасило бы разом все, и переключаться было
бы некуда. `llm_calls.engine` при этом остался провайдером (`PROVIDER = 'gemini'`):
рядом есть колонка `model`, и дублировать её значением `engine` значит потерять
возможность сложить расход по провайдеру. Потребители `translated_by` сравнивают
по префиксу (`LIKE 'gemini%'`, `str_starts_with`) — у записей до 24.08.2026 там
просто `gemini`, и точное сравнение молча выкинуло бы либо архив, либо новые
посты. Колонка расширена до 64: имена превью-моделей Google доходят до 35
символов, а на strict-режиме первый же такой пост падал бы с «Data too long».

Список моделей собирает **только** `GeminiTranslator::chainModels()`. Копия в
плитке состояния уже успела разойтись с оригиналом на значении `'0'`, а
разойдясь сильнее, плитка спрашивала бы предохранитель не тем именем и вечно
показывала «модель работает», пока перевод идёт скрейпером.

`budget_seconds` (240) — бюджет на **статью целиком**, выведенный из
`StorePostJob::$timeout = 420`, поэтому он делится между моделями цепочки. Будь
он поэкземплярным, три модели дали бы потолок 720 секунд: джоба убивалась бы по
таймауту и вместо статьи сохранялась заглушка — ровно та беда, ради которой
бюджет и заводился.

**«Среднее время ответа» считается только по `kind = html` и только по вызовам
с `attempts = 1`.** Заголовок отвечает за полсекунды против десятков секунд у
статьи, а длительность с повторами включает сон между попытками, то есть
приписывает модели время, которое мы прождали сами; смешав их, получаем число,
не описывающее ни то ни другое. Виджет читает таблицу **одним** запросом с
`GROUP BY model` и досуммирует в PHP: длительность хранится суммой и числом
замеров, потому что среднее из средних по моделям равно правильному только при
одинаковом числе вызовов у каждой.

Запись обёрнута в `LlmCall::recording()`: отказ журнала (окно деплоя, диск) не
имеет права стоить статьи, ради которой всё затевалось, но и молчать не должен —
уходит предупреждением в лог. Из-за этой же защиты `GeminiTranslatorTest`
понадобился `RefreshDatabase`: без миграций тесты остались бы зелёными, а расход
не считался бы вовсе.

Чистка — `php artisan llm-calls:prune` (180 дней, есть `--dry-run`), еженедельно
в планировщике. Год держать незачем: за год сменятся и версия модели, и прайс,
а пересчитывать старые токены по новой цене — выдумывать историю.

Плитка **«Переводчик»** живёт в `ParsingStatusOverview` на дашборде, а не в
аналитике: отказ LLM — единственная поломка конвейера, которая ничего не ломает
видимо (очередь идёт, статьи выходят, просто переведены скрейпером). Виджет
опрашивается раз в 10 секунд, размыкатель держится 5 минут — авария попадает на
глаза, пока она идёт. Состояние размыкателя отдаёт `FallbackTranslator::isDown()`;
ключ кэша остался приватным, иначе он расползётся по вызывающим и разъедется с
`markDown()`. Имя движка плитка спрашивает у `GeminiTranslator::name()`, а не
пишет литералом: разъехавшись с ним, литерал заставил бы `isDown()` вечно
отвечать «жив» — то есть плитка соврала бы ровно в той аварии, ради которой
заведена. Формулировка последствия зависит от `translation.fallback`: при
выключенном откате отказ модели означает не «переведёт скрейпер», а «статья
останется без перевода», и обещать откат было бы прямым враньём.

### Перепарсинг не имеет права ухудшать статью

`PostService::keepExistingContent()` — единственная защита сохранённого текста,
и она закрывает два случая, а не один. Первый исходный: разбор не дал контента
вовсе (сбой скачивания, съехавший селектор) — тогда от новой попытки берётся
только отметка о сбое.

Второй появился 24.08.2026 и стоил живого перевода. Контент разбор дал, но
непереведённый: у модели кончилась суточная квота, скрейпер получил 429 на
каждом блоке 44-килобайтной статьи — и поверх полного русского текста поста 236
(`translation_incomplete = 0`, 11 934 символа кириллицы) лёг английский
оригинал. Единственным следом осталась галочка «перевод неполный»;
восстанавливали из ночного бэкапа. **Любой перепарсинг в момент, когда
переводчики недоступны, уничтожал перевод молча.**

Мера — кириллица, а не флаг `translation_incomplete`: флаг сообщает, что о себе
думает переводчик, а вопрос стоит о тексте, и скрейпер в том инциденте
отчитался частичным успехом. Порог — половина: запас на честную переработку
статьи у источника. Асимметрия намеренная — отказ перезаписать в худшем случае
лишает нас обновления (оно повторится или правится руками), перезапись
уничтожает работу безвозвратно.

Вместе с текстом возвращается и `translated_by`: подписать сохранённый перевод
именем движка, который только что провалился, значит соврать в том самом поле,
по которому выбирают, что переводить заново.

**`translated_by` вообще пишется по результату, а не по тому, кто взялся за
работу** (`StorePostJob::translateContentNodes` и `TranslateService` — оба
пути). Сравнивается текст до и после: совпал — значит `TranslationResult::NO_ENGINE`.
Именно сравнение, а не поиск кириллицы: у статьи, где вся проза в заголовке, а
тело сплошной `<pre>`, кириллице в теле взяться неоткуда, и она переведена
корректно.

### Роботы и источники переходов

Просмотром считается только заход человека. До 17.08.2026 в `post_views` шёл
любой GET страницы поста: на проде это давало 589 сессий с 311 адресов при 1212
записях — у отдельных IP до 39 разных сессий, то есть cookie не держались вовсе.
Счётчик под статьёй завышал число читателей, «Популярное» на главной и «Топ
постов» ранжировали материалы по интересу краулеров.

Отсев делает **глобальный скоуп `PostView::HUMANS_ONLY`**, а не условие в
запросах: читателей у таблицы четыре и они разнородны (`Post::viewsCount()`,
`withCount('views')` в популярных постах и в топе аналитики, `Trend` в графике).
Локальный скоуп пришлось бы дописывать в каждом — ровно так уже разъезжалось
условие «раздел с опубликованными постами». Снимать скоуп нужно там, где робот
и есть предмет разговора: дедуп визитов ищет прошлую запись
`withoutGlobalScope(PostView::HUMANS_ONLY)`, иначе помеченный краулер каждый раз
выглядел бы новым посетителем. **`PostViewsOverview` читает таблицу через
`DB::table()`, мимо Eloquent — там фильтр стоит вручную**, и это закреплено
`PostViewAudienceTest::test_overview_tiles_ignore_crawlers` (рендером страницы
не ловится).

Признак робота даёт `App\Support\BotDetector` по User-Agent. Сам заголовок **не
сохраняется** — это часть отпечатка браузера, а вся таблица построена на
неидентифицируемости посетителя; в БД идёт один бит. Детект заведомо неточен в
обе стороны, поэтому запись робота сохраняется с флагом, а не отбрасывается:
ошибку детектора можно пересмотреть, потерянную строку — нет. Подстрока `bot`
ловит `Cubot` (марка смартфонов), для таких случаев в детекторе есть список
исключений — требовать границу слова нельзя, в `Googlebot` перед `bot` стоит
буква.

От реферера хранится только хост (`referer_host`): путь и query чужой страницы
— чужие данные, а на вопрос «откуда трафик» отвечает домен. Хост нормализуется
`PostViewService::normalizeHost()` — нижний регистр, срез `www.` и завершающей
точки, проверка алфавита: `parse_url()` отдаёт хостом и `<script>alert(1)<`, а
`habr.com.` иначе встал бы в отчёте отдельной строкой, то есть разбить топ
источников мог бы кто угодно одним заголовком.

**Переход внутри сайта пишется собственным хостом, а не `NULL`.** Три разные
вещи обязаны различаться: `NULL` — реферера не было (прямой заход), свой хост —
навигация по блогу, чужой — источник. Свалив первые два в `NULL`, отчёт называл
бы прямыми заходами всю внутреннюю перелинковку, а это большинство просмотров;
восстановить разделение потом нечем. Виджет показывает их отдельными строками.

Метки `utm_*` приходят из адресной строки, то есть пишет их кто угодно: отсюда
обрезка по длине, отказ от нескалярных значений (`?utm_source[]=a` иначе ронял
бы показ статьи) и ограничение алфавита. Обратная сторона: метка — сама по себе
идентификатор, и ссылка с уникальным `utm_campaign`, отправленная конкретному
человеку, связывает его с `ip_hash`. HMAC от этого не спасает, поэтому метка
хранится только как короткий идентификатор кампании.

Граница `PostView::ATTRIBUTION_SINCE` (17.08.2026, день выката) делит данные на
«до» и «после», и её знают оба потребителя. У ранних записей `referer_host = NULL`
значит «неизвестно», а не «прямой заход», поэтому **виджет источников их не
считает** — на периоде в квартал они бы весь отчёт и составили. И наоборот:
разметка задним числом (`php artisan post-views:mark-bots`, признак — сколько
разных сессий пришло с одного IP, есть `--dry-run` и `--reset`) работает
**только до этой даты**. Без верхней границы эвристика съедала бы живых
читателей — четыре сессии с адреса даёт обычный офис за NAT, — а `--reset`
снимал бы флаг и с записей, размеченных по User-Agent, восстановить которые
нечем.

### Пустые категории и теги

Ссылаться можно только на раздел, в котором есть хоть один опубликованный пост:
`Category::hasPublishedPosts()` / `Tag::hasPublishedPosts()` — один скоуп на обе
карты сайта, оба листинга и сайдбар главной. Раньше условие стояло дословно в
шести местах и разъехалось: `sitemap.xml` фильтровал, а `/sitemap`,
`/categories` и `/tags` перечисляли `Category::all()` — и вели на разделы с
нулём материалов. Теги страдают сильнее категорий: их проставляет
`TagDetectorService` прямо при парсинге, задолго до публикации.

Сама страница пустого раздела остаётся доступной (200), но отдаёт
`robots: noindex, follow` — адреса, которые Вебмастер уже проиндексировал,
иначе из выдачи не уйдут. Не 404: посты в разделе появятся при следующей
публикации, а отданная единожды 404 выбьет адрес насовсем. Условие —
`$posts->isEmpty()`, а не `total() === 0`: последнее считает пустыми только
разделы без постов вообще и оставляет открытым `?page=99` наполненной
категории — нулевой список, канонический сам на себя.

### Models & Relationships

- `Post` — `belongsToMany(Tag)`, `belongsTo(Category)`, `hasMany(Comment)`, `hasMany(PostLike)`. Uses `SoftDeletes` and `Searchable` (Laravel Scout → Meilisearch). `permalink()` — публичный адрес с учётом `is_news`
- `User` — roles: `ROLE_ADMIN = 0`, `ROLE_READER = 1`. Implements `FilamentUser` for Filament access
- `Release` — stores source URLs for the scraper pipeline

### Broadcasting

Uses **Laravel Reverb** (WebSocket server). Events: `UserNotification`, `PostLiked`. Channel configuration in `routes/channels.php`.

### Search

Laravel Scout with **Meilisearch** backend (container on port 7720→7700). Meilisearch master key configured via `MEILISEARCH_KEY` env var.

### Frontend

Blade templates for the public site; the admin UI is Filament's own. **Livewire 3** powers Filament. Vite for asset bundling.

Демо-страница `/counter` из туториала Livewire (`app/Livewire/Counter`, макет `components/layouts/app.blade.php`) удалена 13.08.2026: она отдавала 200, не была закрыта в `robots.txt` и рендерила `<head>` без описания и без `robots` — единственная такая страница на сайте, из-за которой Яндекс.Вебмастер продолжал показывать «Отсутствуют метатеги &lt;Description&gt;» уже после общего фикса метатегов. Описание гарантируют только макеты (`layouts.main` через композер в `AppServiceProvider`, `layouts.app` через фолбэк), поэтому любая страница мимо них снова окажется пустой.

Вместе с демо-страницей удалён `components/layouts/app.blade.php` — макет full-page компонентов Livewire по умолчанию. Своих full-page компонентов в проекте нет, а если появится, Livewire упадёт с «View not found»: это нужное поведение, макет надо завести заново с метатегами, а не восстанавливать `livewire:publish`. В `SeoFeedSitemapTest` адреса без параметров теперь берутся из таблицы маршрутов (страницы с параметрами по-прежнему перечислены поимённо), так что следующая такая страница упадёт в тестах.

### Deployment

Laravel Envoy (`Envoy.blade.php`) deploys to production via SSH using a timestamped releases strategy (keeps last 5 releases). Requires env vars: `DEPLOY_USER`, `DEPLOY_USER_KEY`, `DEPLOY_SERVER`, `DEPLOY_REPOSITORY`, `DEPLOY_PATH`.

After `envoy run deploy`, reload Apache — mod_php caches realpath and keeps serving the previous release for about two minutes otherwise.

### Long-running services on production (outside the deploy)

Четыре вещи живут рядом с приложением и **не** пересоздаются `envoy run deploy`:

- **Reverb** (WebSocket) — supervisor program `blog-reverb`, listens on `127.0.0.1:8080`, proxied publicly by Apache at `/app`. The deploy does restart it, otherwise it would keep executing code from a release that gets purged.
- **FlareSolverr** (headless browser) — Docker container, `127.0.0.1:8191`, used by the parser to get past antibot challenges that require JavaScript (`config/releases.php` → `challenge_solver_url`). Recreate with `./vendor/bin/envoy run challenge-solver`; the deploy deliberately leaves it alone since it survives reboots via `--restart=unless-stopped` and recreating would drop the browser session.
- **Cron планировщика** — `/etc/cron.d/blog-scheduler`, ставится командой `./vendor/bin/envoy run scheduler-cron`. Без него `app/Console/Kernel.php` не выполняется вообще. Именно так и было до 11.08.2026: расписание с `backup:run` лежало в коде с 3 августа, а бэкапов физически не существовало. Запись от `www-data` — под тем же пользователем работают Apache и `queue:work`; под root артефакты в `storage/` получали бы `root:root` и отбирали запись у веба.
- **Tesseract OCR** — системный пакет `tesseract-ocr` + `tesseract-ocr-eng`, ставится командой `./vendor/bin/envoy run ocr-install`. Им `DiagramTranslatorService` читает текст на картинках (диаграммы, скриншоты, обложки), чтобы перевести его на русский. Локально пакет ставит `docker/8.4/Dockerfile`, на сервере ставить было некому — и до 17.08.2026 перевод текста на картинках **не сработал ни разу**: 124 записи «no text detected» и ноль перерисовок. Причину скрывал `2>/dev/null`, дописанный к вызову: «command not found» приходил пустой строкой, неотличимой от «на картинке нет текста». Теперь вызов идёт через `Illuminate\Process` со списком аргументов, а неудачный запуск логируется как предупреждение (`config/releases.php` → `ocr_binary`, регрессия закрыта `DiagramTranslatorServiceTest::test_missing_ocr_binary_is_reported_as_a_problem`). Отрисовке перевода нужен ещё шрифт с кириллицей — `fonts-dejavu-core`, без него GD молча рисует пустоту.

### Перевод текста на картинках

Единица перевода — **параграф**, а не строка: фраза, разорванная переносом,
уходила в переводчик половинками, и «The Easiest Way to Look Up / GeoIP in
Laravel» превращалось в «Самый простой способ посмотреть вверх».

Обложки переводятся в режиме `headingOnly` — только самый крупный блок текста
(`StorePostJob::translateCoverImage()`, флаг `--heading-only` у
`image:translate`). Причина в геометрии: Tesseract сваливает значок автора, его
имя и логотип DEV — разнесённые по разным краям картинки — в одну «строку»,
её bbox тянется через всю ширину, и закраска стирает логотип просто потому, что
он внутри. Плюс имя автора переводить нельзя, а отличить его от текста нечем.
Крупный блок ищется по **медиане высот слов**: логотип высотой 51px внутри
мелкой подписи задирает габарит строки до 70px заголовка, и по габариту подпись
проходит фильтр целиком.

**OCR запускается с `-l eng+rus`, и текст с долей кириллицы ≥ ⅓ не
переводится.** Это не перестраховка: массовый прогон по архиву 17.08.2026
показал, что часть обложек уже была на русском, английская модель прочитала
кириллицу как латиницу («Топ-16 обязательных ресурсов» → «Ton-16 pecypcosB»),
и перевод этого мусора лёг поверх нормального текста. Файл перезаписывается на
месте — без бэкапа потеря безвозвратна. На английских картинках вторая модель
ничего не меняет: замерено на обложке dev.to, те же 19 слов и та же средняя
уверенность 88.

**Массово по архиву гонять нельзя.** Обложки трёх разных видов, и режим
рассчитан на один: стандартная dev.to (переводится хорошо), уже русская
(теперь отсеивается) и дизайнерская иллюстрация с логотипами и метками
(«PHP», «Xdebug», «VS Code») — на таких либо OCR ничего не находит, либо
перевод разрушает композицию. Отличить обложку от иллюстрации автоматически
нечем; это задача для модели, которая видит картинку целиком.

### Обложка не выводится в теле статьи

`post/show.blade.php` показывает `main_image` только через `og:image` и
JSON-LD; секции с картинкой над текстом нет намеренно. У переводных статей
обложка — это og:image площадки-источника, а он по построению состоит из
заголовка статьи, имени автора и логотипа площадки: прямо под `<h1>` висел тот
же заголовок ещё раз, по-английски и с чужим брендингом. Перевод картинки
проблему не решал, а усугублял — дубль становился русским, ещё и с огрехами
распознавания («GeoIP» → «GeoP»).

В превью ссылки (мессенджеры, соцсети) такая картинка, наоборот, уместна,
поэтому из `og:image` её не убирали. Побочный эффект — со страницы ушёл
LCP-элемент: самым большим объектом первого экрана была картинка с текстом,
который и так есть разметкой. Регрессия закрыта
`PostShowControllerTest::test_cover_is_not_shown_in_the_article_body_but_stays_in_link_preview`.

Картинок внутри статей это не касается — они лежат в `content` и выводятся как
были; именно ради них и нужен OCR-перевод.

### Бэкапы

`spatie/laravel-backup`, расписание в `app/Console/Kernel.php`: `backup:clean` в 01:00, `backup:run` в 01:30, `backup:monitor` в 06:00 — все под `environments(['production'])`.

- Архив шифруется AES-256 паролем из `BACKUP_ARCHIVE_PASSWORD`. **Пароль обязан храниться вне сервера**: он лежит в том же `.env`, который пропадёт вместе с машиной.
- `.env` намеренно исключён из архива — восстановление двухсоставное: архив + `.env` из менеджера паролей.
- `storage_path('app/public')` включён в `include` явно. На проде `storage/app` — симлинк в `shared/`, а `follow_links = false`: без явного пути картинки постов (единственное, чего нет в git) в архив не попадали.
- Каталог архивов зовётся `blog` (`BACKUP_NAME`), а не `APP_NAME`: пробелы и кириллица в пути ломают ручной `rsync`/`scp` при восстановлении.
- Системный `unzip` эти архивы распаковать не может («unsupported compression or encoding» — он не знает WinZip AES). Восстанавливать через `7z x` или PHP `ZipArchive::setPassword()`.

`--memory=900m` for FlareSolverr is not arbitrary: with 512m Chrome fails to finish the challenge and the service returns `Timeout after 60.0 seconds`. The peak is only needed while solving — at rest the container holds ~110 MB.

`composer.json` pins `config.platform.php` to the production PHP version. Raise it only together with PHP on the server, otherwise the lock resolves against the local (newer) PHP and produces a set of packages that cannot be installed on production.
